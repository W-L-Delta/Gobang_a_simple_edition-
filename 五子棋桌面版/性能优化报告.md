# 五子棋桌面版 · 规则审查与后端性能优化报告

日期：2026-11-21  
范围：`engine.py`（规则 + AI）、`main.py` 中与 AI 调度相关的部分、`五子棋.exe` 重新打包。

---

## 一、结论

1. **胜负判定没有出现参考里提到的两个经典 bug**：它以最后一手为中心、四个方向**双向**计数，并且计数封顶到 6，能区分“恰好五”和“长连”。边线五连、角落五连、落子居中成五、黑长连禁手、白长连胜、双四、三三、五连优先等用例全部通过。
2. 真正的问题集中在**性能与并发**：
   - 原实现的 `_build_run_at` 在每次判定时构造 Python 列表并反复调用 `in_bounds/row_of/col_of`，是 profile 的第一热点；
   - AI 每个搜索节点对全部候选点做两次“放置—四方向建列表”的成五扫描；
   - 候选点、点评分、整盘评估都在每个节点全量重算；
   - 困难模式 1.15 秒内只搜索约 300–500 个节点；而且根循环超时后，剩余根着法直接返回静态评估，**可能漏掉最佳着法**；
   - 重开/悔棋只递增 `game_token` 丢弃结果，**旧 AI 线程仍会跑满 1.15 秒**，连续重开会叠加多个线程抢 CPU。
3. 优化后（规则语义完全不变）：
   - 黑棋禁手判定 **约 14 倍**；
   - 同深度搜索 **约 6.6 倍**；
   - 困难模式同一 1.15 秒预算内节点数 **约 5.9 倍**，并改用迭代加深，能在预算内完整搜到 root+5（旧版名义 root+4，且通常只完整搜完第一个根着法）；
   - AI 搜索支持取消，重开/悔棋立即停止旧线程。

## 二、发现的问题

### 2.1 规则与胜负判定

已核对并通过的部分：

| 用例 | 结果 |
| --- | --- |
| 黑棋在五连正中间落子（左右各两子） | 判胜，`win_line` 覆盖两侧 |
| 横向 / 纵向 / 主对角 / 反对角五连 | 判胜 |
| 边线（第 0 行）五连 | 判胜 |
| 黑棋六连（长连） | `analyze_move` 判禁手，`check_win` 不判胜 |
| 白棋六连 | 判胜（白棋无禁手，长连算胜） |
| 黑棋恰好五连 | 合法且判胜 |
| 双四 | `forbidden=True`，`reasons=('doubleFour',)` |
| 双三 | `forbidden=True`，`reasons=('doubleThree',)` |
| 一手成五 + 双四 | 五连优先，判胜 |
| 满盘 | 平局 |
| 白棋双三 | 合法 |

仍属于“规则取舍”、不是代码错误，但值得知道：

- `count_threes_at` 只承认“再填一子能形成直四”的三，并且会排除延伸后成五/长连/双四的“假三”。职业连珠中极少数需要多层递归验证的三三，这里会简化（README 已注明）。
- `count_fours_at` 按“不同的四子组合”去重。我们穷举验证过，**同一方向上确实可能产生两个不同的四**（例如 `.#.#.#.#` 这种形状），这属于常见的“同线多四”判法，但与部分职业规则定义可能存在差异。
- 棋盘是 **14×14**，不是标准连珠 15×15；`CENTER_POINTS` 用了 4 个中心点。网页版也是 14 路，所以更像有意设计，建议确认而不是直接改。
- `is_legal_move` 和 `analyze_move` 是两套几乎重复的完整判定；`main._place_move` 又调用了一次 `is_legal_move`。一次点击会做 2–3 次相同的禁手分析。本次通过加速底层解决了耗时，没有合并接口。

### 2.2 性能热点（原始引擎 profile）

在一个 12 子中局、困难模式、1.18 秒的 profile 中：

| 函数 | 调用次数 | 主要耗时 |
| --- | ---: | ---: |
| `_build_run_at` | 189,087 | 0.518 s（累计） |
| `in_bounds` | 871,140 | 0.198 s |
| `_quick_point_score` | 19,364 | 0.269 s（累计） |
| `get_candidates` | 333 | 0.111 s |
| `winning_line_for` / `get_runs_at` | 44,506 / 44,798 | 0.633 s（累计） |
| `evaluate_board` | 208 | 0.031 s |

具体原因：

1. 每次胜负/禁手判定都 `list.append` + `list.insert(0, ...)` 重建整段连珠，并逐步做行/列换算和越界判断。
2. `get_candidates` 每个节点全盘 196 格扫描，每颗子再检查 24 个邻格。
3. `_minimax` 在每个内部节点对约 100 个候选点各做一次成五扫描（先后两次：自己、对手），每次扫描 4 个方向并建列表。
4. `quick_rank_moves` 对每个候选点分别计算进攻分和防守分；`placement_score` 还依赖正则匹配 11 格窗口。
5. `evaluate_board` 每次扫描 66 条线、约 744 个格位，只在叶节点调用，占比不大但会随节点数增长。

### 2.3 搜索与时间管理

- 固定深度 4、根宽度 10，没有置换表、没有迭代加深、没有杀手/历史启发。
- `_minimax` 在入口检查 deadline；一旦超时，后续节点直接返回静态评估。根循环仍会继续，于是**排在后面的根着法可能只得到静态分**，而不是被搜索。这是比“慢”更值得修的问题。
- 旧版在 `depth<=0` 之前还会做一次全量成五扫描，相当于叶节点多算一层；这提升了战术视野，但也是搜索时间的大头之一。
- 评估函数只按双方棋型差计分，没有体现“轮到谁走”；组合威胁（双活三、四三）只有固定加分，仍是线性近似。

### 2.4 并发与交互

- **旧 AI 线程不可取消**：`start_new_game` / `undo_move` 只递增 `game_token`，工作线程继续把 1.15 秒跑完。连续重开或快速悔棋会叠加多个搜索线程。
- 终局后不能悔棋：`player_can_play()` 要求 `phase=="playing"`，而 `_end_game` 把 `phase` 设为 `"over"`；本地模式同样在 `phase != "playing"` 时直接返回。
- 每次落子 `canvas.delete("all")` 全量重绘；胜利时 `_place_move` 先重绘一次、`_end_game` 又重绘一次。
- 没有调用 `SetProcessDpiAwareness`，Windows 高缩放比下窗口可能被系统位图拉伸而发虚。
- `random.choice` 用于开局和同分着法，同一局面可能给出不同结果，不利于复现问题（参考里也提到这一点）。

## 三、做了哪些优化

### 3.1 `engine.py`

保持所有公开函数名、参数和返回结构不变；规则语义通过差分测试确认一致。

1. **预计算方向射线表** `POS/NEG/NEXT/PREV`：每个格点、每个方向的有效索引直接查表，胜负判定不再做行/列换算和 `in_bounds`。
2. **封顶 6 的 `_line_len`**：数到 6 立即返回，足以区分“恰好五”和“长连”，同时避免构造整段列表。
3. **禁手快速门控**（`_maybe_forbidden`）：在调用递归的 `count_threes_at` 之前，先用严格的必要条件排除绝大多数点：
   - 双四至少需要某个方向在 ±4 格内有 3 颗己方子；
   - 双三至少需要两个不同方向在 ±3 格内各有 2 颗己方子。
   这两个条件是**必要**的（我们另外穷举验证了“单方向最多 1 个三”，并发现“单方向可以有两个四”，因此四的判定仍会进入完整计数）。门控只做排除，不会把禁手误判为合法。
4. **候选点增量邻居计数**：搜索上下文维护 `neighbors[196]`，落子/悔棋只更新 24 个邻格；生成候选点从“每颗子扫 24 格”变为一次 196 格过滤。
5. **增量“成五点”集合**：维护每个玩家“再落一子即成五”的空点集合。落子/悔棋只影响经过该点的 4 条线，刷新 8 个“线—玩家”条目；`_minimax` 的成五检查从“扫描约 100 个候选点”变成 O(1) 的集合判空，同时**保留了旧版在叶节点也能发现立即成五的战术视野**。
6. **更快的点评分**：`_quick_point_score` 改用预计算射线 + 查表分值（`POINT_VALUE`），并保持与原实现逐位一致（差分测试覆盖）。
7. **迭代加深 + Zobrist 置换表**：困难模式从固定深度改为 2..8 层迭代，带时间预算；置换表缓存深度/上下界/最佳着法，用于剪枝和着法排序；先手必胜或预算耗尽时立即返回当前最优。
8. **可取消搜索**：`choose_move(..., cancel=...)` 接受一个无参回调；`_SearchContext` 在节点入口检查，取消后立即停止。
9. **评估内联**：`evaluate_board` 的连段统计划分内联，减少函数调用（该项提升有限）。

### 3.2 `main.py`

- 新增 `self.ai_cancel = threading.Event()`；
- `schedule_ai` 每次新建事件并把 `cancel.is_set` 传给引擎；
- 重开、终局、悔棋、关窗时 `set()` 旧事件，旧搜索会在下一个节点退出，不再空转。

### 3.3 打包与运行环境

重新打包后第一次启动时出现过：

> Error: Could not create temporary directory!

定位过程：

1. 当前用户 `%TEMP%` 可写、磁盘剩余 113 GB，排除空间和普通权限问题。
2. 用 PyInstaller 打了一个最小单文件控制台示例，同样报
   `[PYI-xxxxx:ERROR] Could not create temporary directory!`，说明不是五子棋代码的问题。
3. 单文件模式默认把自身解压到 `%TEMP%\_MEIxxxxx`；当前启动环境（沙箱/安全策略）拒绝该写入。
4. 给最小示例加上 `--runtime-tmpdir "."` 后正常运行，证明把解压目录改到当前目录即可。
5. 五子棋 EXE 用同样参数重打包后，主窗口正常打开（进程标题、`_MEI` 目录均验证通过）。

因此 `build.ps1` 和本次打包都加了：

```text
--runtime-tmpdir "."
```

这样 `_MEIxxxxx` 会创建在**程序当前目录**，不再依赖 `%TEMP%`。注意：请把 EXE 放在可写目录中并从该目录启动；若程序被强制结束，可能残留一个 `_MEIxxxxx` 文件夹，可直接删除。

### 3.4 没有改动的内容

- 棋型权重、评估函数、三档难度的行为策略、根宽度、1.15 秒预算均未改变；
- 双三/双四的判定模型保持原样（包括它的近似边界），没有借优化之名改规则；
- 界面布局、配色、交互流程未动。

## 六、后续建议（按性价比排序）

1. **终局悔棋**：现在输了以后 Ctrl+Z 无效。若要支持，需要在 `phase=="over"` 时也允许回退，并清空 `winner/win_line`、恢复 `current`；本地模式同样处理。
2. **高 DPI**：在创建 Tk 根窗口前调用 `SetProcessDpiAwareness(2)`，并按 `tk scaling` 调整字号；否则 125%/150% 缩放下界面会发虚。
3. **增量重绘**：落子时只添加一个新棋子、悔棋时删除对应 item，而不是 `delete("all")`；胜利时先判胜再统一重绘，避免一次胜利两次全量重绘。
4. **合并重复判定**：`analyze_move` 的结果可以直接传给 `_place_move`，避免同一次点击做 2–3 次禁手分析（目前底层已很快，收益是锦上添花）。
5. **组合威胁与先手评估**：若要继续提升棋力，可把“双活三/四三”从线性加分改成显式棋型组合，并在评估中加入“轮到谁走”的修正；再往上是 VCF 算杀。
6. **可复现性**：把开局/同分着法的 `random.choice` 换成可配置种子，便于复现 AI 行为。
7. **时间预算**：如果希望困难模式“想得更短”，把 `HARD_TIME_LIMIT` 从 1.15 调到 0.85–0.9；按当前速度仍能完成 root+5，界面反馈会明显更利落。

## 七、一句话总结

这套程序的规则判定**没有参考里那两个经典错误**，主要问题是“用最贵的方式做最频繁的判定”和“AI 线程不可取消”。本次在**不改变规则语义和手感**的前提下，把规则判定提速约 14 倍、同深度搜索提速约 6.6 倍，并把困难模式的时间预算真正花在了“搜完全部根着法、再深一层”上。
